Button Consolidation POC

Lightning Design System · branch feature/button-poc · 2026-07-15 · source of truth: assets/packages/ui/docs/poc/button-risk-log.md · verifiable inventory: assets/packages/ui/docs/poc/button-manifest.md

TL;DR. One canonical Button now exists per stack — lib/lightning_web/components/ui/button.ex (HEEx) and @openfn/ui's Button.tsx (React) — both styled from one shared recipe, assets/packages/ui/recipes/button.json. 175 existing component call sites carried over unchanged; 2 duplicate implementations deleted; 6 raw one-offs migrated; the remaining 61 raw buttons were classified, not force-migrated — 90% of them turn out to be the anatomy of other components (27 are one identical modal-close X). Both stacks now also carry icon-only buttons and a SplitButton (HEEx twin built from the app's own Phoenix.LiveView.JS/phx-click-away conventions), with matching a11y/i18n guarantees. Four real bugs were found and fixed by actually loading components in a browser, not by trusting class-string tests — see §6c. Full test suite green (only pre-existing flakiness that also fails on main).

1. Who this serves

The UX designer (Tyrell)

Wants exactly one Button per stack matching the Figma "Buttons" set; every button in the app an instance of it; Figma vocabulary for variants/sizes, with Warning→danger as the one logged exception.

How this serves them: one recipe now defines every button's look; the two stacks can no longer drift (a live secondary-variant drift was found and killed); a ghost variant formalizes the most common one-off; the storybook story now shows the real component. Divergences that need design decisions are logged, not decided unilaterally.

The engineers

(X) zero regressions across 175 call sites, esp. submit semantics; (Y) reviewable, mechanical, batched diffs; (Z) no new maintenance burden and a small stable API.

How this serves them: the canonical HEEx button is a verbatim move — all 175 call sites compile untouched; rendered class sets proven identical; each migration is its own commit with a risk entry; a compile-time guard fails the build if recipe and component API disagree; grep gates provided for CI.

4. Subtleties, hard parts, judgment calls

  1. Warning vs danger. Kept danger (code vocabulary); Figma says Warning. Logged as the known Phase 0 naming gate. Complication discovered: HEEx already has a separate warning (yellow) theme with 1 call site, plus success (2) — neither is in Figma. The recipe carries both; the designer needs to rule on their future.
  2. Radius divergence. Figma buttons read ≈rounded-lg; production is rounded-md. Recipe encodes production. Not resolved unilaterally.
  3. The 175 wasn't wrong — but two inventory rows were. cancel_button is a composition, not a duplicate (kept); button_loader was dead code (deleted, no loading state built). Audit-by-reading needs verify-by-grep before migration — exactly what this loop does.
  4. Most raw buttons belong to other components. 27 of 61 remaining are ONE identical modal-close X (the HEEx twin of React's nakedClose); 9 are table-action/icon-button utilities; plus toggles, tab bars, radio cards, chip dismissals, link-styled buttons. Force-migrating them would bloat Button's API (padding-less sizes, switch styling). Judgment call: defer each to its owning component. One future Modal close-slot change retires 27 one-offs at a stroke.
  5. Submit semantics preserved by construction. type="submit" is a first-class attr; phx-disable-with/phx-click/onclick flow through :global; disabled is in the include list. The one migrated submit (project Save) is covered by 130 green LiveView tests.
  6. Recipe compile-time loading. HEEx reads the JSON at compile time (@external_resource → edits recompile; zero runtime cost; works in releases). Trade-offs accepted: an assets/ file now participates in the Elixir build (Docker build ordering must copy it before mix compile — CI note), and a compile-time guard fails the build if recipe keys and component attrs diverge (drift caught at compile, not in prod).
  7. Disabled-cursor divergence kept per stack. HEEx ships disabled:cursor-auto, React disabled:cursor-not-allowed (and ui-patterns.md mandates not-allowed). Unifying is a one-line recipe change once the designer picks; preserving production exactly won this round.
  8. Packaging deferred. Recipe lives at assets/packages/ui/recipes/ (the plan's target path), but the React Button stayed in place importing it — npm-workspace wiring was not needed to test the recipe idea and would have been a yak-shave in this POC.
  9. Environment findings (not POC changes, logged for the team): stale crc32cer CMake cache and a pre-commit hook line 3 both still point at the repo's old path (…/Projects/lightning); the lightning-postgres container was stopped. First fixed properly, second is harmless but should be fixed, third restarted.
  10. Skipped/reverted entries: none were forced. Nothing hit the stop conditions (no Yjs internals touched, no breaking API change needed, tests stayed green). The frozen legacy editor received exactly one import line, which its 14 existing <.button> refs made compile-mandatory.

6. Overall merge risk: LOW-MEDIUM

  1. No pixel-level verification anywhere. All equivalence is at the class-string level. Mitigation: boot the dev server and eyeball 5 screens (project settings Save, backup codes, user-deletion modal, AI assistant panel, any collab-editor modal) before merge — 15 minutes; or land Phase 2's visual-regression harness first.
  2. React secondary hover changed in the collab editor (drift unification). Mitigation: designer sign-off on the side-by-side in §3; revert is a one-line recipe edit.
  3. Recipe couples the Elixir build to an assets file. A missing/renamed recipe breaks compile (by design), and container builds must copy assets/packages/ui/recipes/ before mix compile. Mitigation: verify the Dockerfile copies assets before compile (it copies the app dir wholesale today); the compile guard turns silent drift into loud failure.

7. Verdict — what this proves and disproves about the plan

Proved:

  • The shared recipe works and is not theoretical. It immediately exposed a real production drift (React vs HEEx secondary), Tailwind compiles classes straight from the JSON, both stacks consume it naturally (compile-time / import), and a compile guard makes divergence loud.
  • Verbatim-move + recipe is a safe repoint pattern for a 175-site primitive. Zero call-site churn, warnings-as-errors caught every loose end, class-set equivalence is provable without screenshots.
  • The batch + risk-log workflow is sustainable — each switch is minutes of work once the harness exists; the log writes itself as you go. For 124 components the constraint is reviewer attention, not build effort, matching the plan's revised bottleneck.

Disproved / must change in the plan:

  • The Phase 5 "one-off cleanup" framing is wrong. The 67 raw buttons are ~90% other components' anatomy. Re-cut cleanup batches per OWNING component (Modal's close slot alone retires 27). The master sheet's MIGRATE rows should be re-tagged with owners before batching.
  • Inventory rows must be verify-by-grep'd at execution time — two of nine button rows were wrong (cancel_button misclassified, button_loader dead). Cheap to check, expensive to trust.
  • Visual verification must come before broad migration, not after — this is no longer theoretical. §6c is direct evidence: a broken storybook, missing fonts, an entirely invisible icon, and a 2px-off-center icon all compiled cleanly, passed every ExUnit/Vitest assertion, and were caught only because a reviewer opened a real browser and looked. Phase 2 (Storybook + visual regression) isn't a nice-to-have prerequisite, it's the only mechanism that would have caught any of these four bugs automatically.

New design gates surfaced for Phase 0: success/warning themes' future, ghost weight/colors vs Figma Ghost, disabled-cursor policy, the close-affordance treatment (nakedClose ⇄ 27 HEEx close X's).
